# Контрольный запуск pipeline-001

Перед отправкой замените MODEL_LABEL фактическим названием модели и настройками (провайдер, reasoning, режим Cline). Для сравнения версий HST модель и настройки сохраняются одинаковыми. Для сравнения моделей версия HST должна быть одинаковой.

```text
Выполни полный технический контрольный прогон HST pipeline-001.
MODEL_LABEL: <фактическая модель и настройки>

Создай новую изолированную папку runs/HYP-YYYY-MM-DD-NNN с очередным свободным ID. Существующие прогоны не продолжай и их результаты не читай. Это явное разрешение создать новую папку и выполнить весь прогон.

Возьми FRAMEWORK_DIR/benchmarks/pipeline-001/hypothesis.md. Скопируй в RUN_DIR/input/hypothesis.md дословно: замени только {{HYPOTHESIS_ID}}, {{DATE}} и {{RUN_ID}}. Не переформулируй гипотезу, контекст или роли. Статус при старте draft.

Для установленной 2.9 используй диалоговый запуск из implementations/dialogue-run.md: native-файлы, execution_driver=dialogue, без Python-preflight, prepare/viewer/start. Название модели и настройки сохрани дословно из MODEL_LABEL; если не указаны — null, не угадывай их по Cline. Для установленной 2.8 используй её штатный prepare с --benchmark-case pipeline-001 и --model-label. Не переносить команды 2.9 в старый фреймворк.

Все три источника я явно отключаю для этого запуска: локальная БЗ, Confluence и интернет. Сохрани все три канала как false в source_selection по контракту установленной версии с основанием «Явный выбор пользователя в контрольном сценарии pipeline-001». Не спрашивай этот выбор повторно. Инструкции/шаблоны/ролевые материалы самого фреймворка можно читать: они не являются эмпирическими данными заказчика.

Проверку полноты найденных материалов явно пропускаю: зафиксируй retrieval review как waived с этим основанием. Другие проверки качества и финальный аудит сохраняются. Синтетические ролевые ответы не считать доказательствами.

Продолжи hst-run для этого RUN_DIR до human_report.html и полной проверки. В 2.9 проверяй уже созданные результаты через validate_runs --phase/--pending-report --save-report; не используй контроллер для переходов. В 2.8 применяй complete/finish по её правилам. Не изучай чужие прогоны и controller-results.md, не тестируй checker искусственными FAIL и не пиши заведомо неправильные сроки/статусы. Ошибки, возникшие реально, сохрани в истории и исправь в согласованных границах.

В финале сообщи результат проверки, ограничения и путь к журналу/имеющимся метрикам. Не создавай фиктивные метрики, если вызовов не было. Не выдавай незарегистрированное время за время размышления модели. Не обещай подтверждение спроса: это технический тест без эмпирики.
```
