# Контрольный сценарий pipeline-001

Сравнение версий HST на одной модели или моделей на одной версии HST. Это технический no-evidence прогон, не подтверждение рынка. Фиксированная карточка — [hypothesis.md](hypothesis.md), готовое сообщение Cline — [prompt.md](prompt.md).

## Условия

- Каждый повтор — новая папка и новый чат, без продолжения старых этапов.
- Для сравнения оптимизации сохраняются модель, reasoning/температура и режим Cline; меняется только версия HST. Для сравнения моделей версия HST фиксируется.
- В карточке заменяются только ID и дата; статус draft/completed не влияет на хеш. Другие изменения отклоняются при prepare --benchmark-case pipeline-001.
- Три источника отключены явным выбором в контрольном сообщении. Изменение каналов через sources-set отклоняется, пока прогон помечен этим benchmark case.
- Проверка полноты материалов явно waived пользователем в сообщении; остальные гейты сохраняются. Ролевые ответы — синтетические, не evidence.
- Фактическая модель/настройки задаются --model-label; HST не угадывает модель. Не меняйте её в середине запуска. Метка — самоотчёт пользователя, не доказательство состава запросов.

## Сравнение со старой версией

В 2.7 ещё нет benchmark-case, model-label, batch-claims и пассивных замеров. Для исходного запуска используйте ту же карточку и отключённые каналы, но штатные команды старой версии без новых флагов; модель/настройки запишите вручную. В новом запуске применяйте prompt.md версии 2.8. Перед выводами сверьте карточки: допустимы только разные ID, дата и статус. Процессные метрики старого запуска восстановить нельзя — сравнение календарного времени требует отдельно учтённых ожиданий или истории Cline.

## Что сравнивать

`outputs/performance_summary.json` создаётся автоматически в новых прогонах, без отдельного вызова модели. Сравнивайте:

1. Полное календарное время в записанном окне журнала.
2. Зарегистрированные ожидания пользователя и разрешений (пересечения объединяются).
3. Число инструментированных команд, их wall/CPU и количество фактических проверок.
4. Число FAIL/ERROR, сохранность рисков, исходной формулировки и ограничений.
5. Неразмеченное время — отдельно; оно включает модель, другие инструменты и незаписанные паузы, а не только reasoning.

Суммарные wall/CPU процессов и вложенные секции нельзя складывать с длительностью прогона: команды/секции могут пересекаться. Standalone validate_runs остаётся read-only и не пишет метрики; вызов полного аудитора внутри finish измеряется. Метрики не охватывают все команды Cline, если они не являются инструментированными CLI HST. Время до первого события, включая начальный диалог, не входит в журнал. Без событий ожидания пауза не вычитается автоматически.

Для исторического прогона сводку можно получить read-only: `python <FRAMEWORK_DIR>/scripts/run_control.py metrics --run-dir <RUN_DIR>`. Отсутствующие данные процессов останутся неизвестными; файлы старого прогона не дополняются автоматически.

## Состояние проверки оптимизации

В первом пакете проверяются измерения, повторные гейты и пакетная регистрация. Содержание десяти этапов и требования к доказательствам сохраняются. На регрессионном этапе Facilitator число семантических проверок внутри одного complete уменьшено с 3 до 1; это число вызовов, не оценка ускорения всей LLM. Проверка finish выполняет один полный аудит и всё ещё отвергает повреждённый отчёт. Пакет утверждений проверяется целиком до одной записи ledger.

Измерение ускорения реального Cline требует контрольных запусков пользователя. До них процент ускорения не заявляется. Компактные планы и автоматическая сборка документов — следующий пакет после сравнения.
