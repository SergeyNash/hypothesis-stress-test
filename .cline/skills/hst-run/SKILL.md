# Выполнение прогона

Прочитай вход и согласованные границы в run.md. Для новой гипотезы — отдельный RUN_DIR; для продолжения — только названная папка. Не ищи успешный старый прогон как образец. Модель анализирует и проверяет содержание; Python-оркестратора и машинных контрактов нет.

При явной просьбе внести полевой результат в завершённый RUN_DIR сразу выполни раздел «Вернуться с результатом проверки» в [диалоговом прогоне](../../../implementations/dialogue-run.md#вернуться-с-результатом-проверки). Обнови историю и оба итоговых резюме в этой папке. Обычная последовательность этапов ниже относится к исследованию гипотезы.

Проходи этапы последовательно, читая инструкции по мере необходимости:

| Этап | Навык | Результат |
| --- | --- | --- |
| Роли | hypothesis-facilitator | role_outputs/*.md, summary и вопросы |
| Локальные основания | local-knowledge-retrieval | preview и evidence_inventory.md |
| Бизнес-контекст | business-context-value-check | анализ либо явные пробелы |
| Рынок | hypothesis-market-layer | market_analysis.md |
| Синтез | hypothesis-synthesis | карта и hypothesis_digest.md |
| План проверки | customer-discovery-planning | customer_discovery_plan.md |
| Критический разбор | hypothesis-decision-review | decision_review.md |
| Итог | human-report-export | human_report.md + human_report.html |

Для service_business используй profiles/service-business.md: стороны ролей, клиентская ценность, покупка, исполнимость, экономика и границы обещания. Не подменяй предметное решение техническим статусом.

Полный запуск разрешает обычное продолжение без повторных подтверждений. В настоящей развилке покажи, что известно, варианты и рекомендацию; задай вопрос в чате и запиши ответ в run.md. При смене гипотезы/источников/глубины или перезаписи завершённых результатов требуется реальное согласование.

Каждый этап добавляет свой вывод и ссылки, не повторяет все предыдущие документы. Пользуйся .clinerules/40-run-quality.md: ответ на вопрос либо явный пробел — точка остановки, не нужно исчерпывать БЗ. Бизнес-контекст внутреннего изменения не требует полного описания новой услуги; неприменимость объясняй.

Читай разрешённые источники средствами клиента. Если формат недоступен — сообщи, не устанавливай парсеры и не придумывай извлечённые данные. Не создавай snapshot, ledger, review JSON, маркеры, payload для Python и технические журналы. Ссылки, точные цитаты, период/единицы и ограничения храни в содержательных Markdown-документах.

После этапа перечитай результат по смыслу: основания/допущения/неизвестное, противоречия, сохранность исходной идеи. Не исполняй checker и не сочиняй замену: PowerShell/Python/shell/regex-проверки, временные TXT-извлечения и циклы отладки запрещены внутри прогона. Не тестируй фреймворк намеренными ошибками в пользовательской задаче. После успешного сохранения результата обнови progress.md фактическим результатом и продолжи согласованный объём.

В финале дай рекомендацию, уверенность, покрытие источников, ограничения и ближайшую проверку; ссылка на outputs/human_report.html для чтения и outputs/human_report.md для текста. Оба файла входят в финальный этап без отдельного разрешения. HTML — статический итог, не HTML-прогресс; сервер/конвертер/JS не нужны. Рекомендацию модели отдели от принятого решения владельца, причём действующее решение и условия должны быть видны в начале отчёта. Запиши завершение и доступное фактическое окончание в progress.md, не получая время из монитора/терминальных команд. Нет технического PASS: завершение означает, что согласованный разбор сделан, а не что гипотеза доказана.
