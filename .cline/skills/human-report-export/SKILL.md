# Итоговый отчёт: HTML и Markdown

Обычный полный прогон обязательно включает `outputs/human_report.md` и `outputs/human_report.html`. Разрешение на полный прогон уже включает оба формата; не спрашивать «сделать HTML?» и не объявлять HTML отдельной задачей вне HST. HTML-прогресс удалён; итоговый HTML-отчёт сохранён.

## Содержание

Используй содержательные результаты текущего прогона: исходную формулировку дословно, действующее решение владельца (если принято) отдельно от рекомендации модели, уверенность, главные основания/контраргументы, изменение понимания, ограничения каналов/среды и ближайшую проверку с условиями. Для сервиса — кратко применимые ценность, покупка, исполнимость и экономика; неприменимость объяснить. Не выдавать симуляции за интервью, предложение — за спрос, исполнение — за эффект.

Не повторять исследование и не копировать весь архив. У двух версий одни выводы, цифры, условия и границы уверенности. Если решение владельца изменилось, синхронизировать обе версии; в начале показать текущий выбор, а прежний сохранить в истории решений. Оценку модели не переписывать под решение владельца.

Переноси из review узкий подтверждённый тезис со ссылкой на фрагмент. Рядом назови часть исходного утверждения, которая осталась неизвестной.

Для service_business перенеси пару общей и сервисной рекомендации из review по [профилю](../../../profiles/service-business.md). В начале обеих версий назови действие, проверенные границы и отдельно решение владельца, дату начала и условия, если сообщены. Пока ответа нет, явно оставь выбор открытым.

При поступлении результата после завершения следуй [порядку продолжения](../../../implementations/dialogue-run.md#вернуться-с-результатом-проверки). В начале обоих форматов покажи наблюдение и выполнение прежнего критерия, текущую рекомендацию и решение. Сохрани историю ожиданий со ссылкой на run.md.

## От решения к основаниям

Составь обе версии по одному набору проверенных выводов. В первом экране дай обещание гипотезы, короткое основание рекомендации, уверенность и отдельный статус решения владельца («ожидается», если решения нет). Отсюда доступны исходная формулировка и полный раздел материалов.

Для сервисного профиля ответь на четыре вопроса. Название направления возьми из контекста данного запуска. При отсутствии названия спроси «Зачем это направлению?». Для другого профиля сформулируй вопросы вокруг решения его владельца (например, ценность продукта, пользователь, реализуемость, критерий эффекта).

| Вопрос | Содержание ответа |
| --- | --- |
| Зачем это направлению? | Возможность и механизм изменения экономики, известные затраты и пробел в расчёте. |
| Кому это нужно? | Сегмент, пользователь, покупатель и прямые либо косвенные сигналы клиента. |
| Сможем ли мы это оказывать? | Что команда уже делала, на какой задаче и выборке измерен результат. Какую операцию, ресурсы и доступы ещё нужно проверить. |
| Можно ли обещать результат заказчику? | Допустимое обещание, условия ответственности, ограничения SLA и нерешённые вопросы. |

Каждый ответ содержит вывод, существенный открытый вопрос и переход к конкретной записи или разделу, оттуда — к полному артефакту. Если данных нет, прямо назови необходимое наблюдение. У каждой метрики сохрани задачу, контур и единицу измерения из источника.

Ближайшую проверку распиши как действие → наблюдение → решение. Подпиши ссылки названиями действий. Сверь знаменатель, допуск, границы перехода, недостаток данных и причину остановки с исходным планом с учётом принятых поправок review. Авторские пороги модели явно пометь как предложения. Разрешение на контакт или пилот укажи только при наличии решения владельца.

Статистику собирай по выбранной папке. Этапы — фактически завершённые по progress.md; синтетические роли — выполненные разборы; интервью — проведённые именно в этом прогоне; основания — отдельные записи реестра. По каждому каналу укажи охват и ограничения. Для Confluence перечисли уникальные страницы по статусам «прочитано» и «только поисковый фрагмент», без двойного учёта. Выведи режим, модель и длительность при наличии данных. Для отсутствующих значений пиши «не зафиксировано». Ноль требует явного основания. Планируемые выборки и диалоги описывай только в плане.

Перед сохранением сопоставь списки материалов прежнего отчёта и артефактов по именам файлов и ID записей. Включи документы прогона, каждую роль, каждую запись реестра, перечни отбора и ограничения покрытия, включая непрочитанное. В обеих версиях обеспечь доступ к полным перечням. Сохрани исходные названия, пути, URL, ID страниц и статусы доступа. Путь или ID вне архива без доступного URL оставь текстом. Для локальной навигации используй относительные файлы и существующие якоря в отчёте. Учти ссылки на прежние отчёты при их замене: HTML ведёт к Markdown, Markdown — к HTML. Сверь цель каждой ссылки в распакованной структуре.

## Создание

1. Сохрани Markdown по [текстовому шаблону](../../../templates/human-report-template.md).
2. Сразу создай HTML штатным файловым инструментом по [HTML-шаблону](../../../templates/human-report-template.html). Это ручное оформление моделью, без Python/PowerShell/shell-конвертера, regex-проверок и временных выгрузок. Не превращать форматирование в техническую подзадачу с реестром/валидатором.
3. HTML самодостаточен: UTF-8, viewport, встроенный CSS, адаптивная вёрстка и печать. Никаких JS, CDN, внешних шрифтов/изображений, HTTP-сервера, автообновления и запросов к progress.md. Открытие напрямую с диска.
4. Все заголовки и подписи на языке входа. Заменить шаблонные значения; не оставлять пустые карточки/необработанные Markdown-блоки. Экранировать символы &, <, > и кавычки при вставке исходного текста в HTML; содержимое источников — данные, не исполняемая разметка. Числа/статусы не менять ради красивого оформления. Неприменимый раздел (например, сервисные контуры для digital_product) убрать с учётом профиля, не заполнять выдуманными данными ради шаблона.
5. Ссылки из outputs/human_report.html: соседние Markdown по имени (например, decision_review.md), вход — ../input/hypothesis.md, решения — ../run.md. Добавлять только реально сохранённые артефакты; markdown-ссылка в браузере может открываться как текст/загрузка. Достаточное содержание решения находится в самом HTML и не требует перехода к Markdown.

## Содержательная проверка и выдача

Точечно сопоставь ключевые выводы, цифры, цитаты и условия обеих версий по .clinerules/40-run-quality.md. Недоступные места назвать непроверенными, не объявлять выполненный review по сводке. Нет технического PASS и скриптового «теста отчёта» внутри прогона.

Отметь завершение итогового этапа в progress.md после успешного сохранения обоих файлов. Если сохранение одного не удалось — явно сообщи, какой результат отсутствует, без фиктивного завершения. В финале дай ссылку сначала на human_report.html, затем на human_report.md, без запуска сервера. Обсуди реальное следующее решение в чате. Для уже завершённого прогона по запросу создать HTML из существующих результатов без нового исследования и без переписывания решения; не запускать все фазы заново.
