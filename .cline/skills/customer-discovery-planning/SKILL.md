# План проверки

Используй исходную гипотезу, решающие неизвестные синтеза и сохранённые основания текущего прогона. Для service_business применяй Validation planning [профиля](../../../profiles/service-business.md). Не выполнять исследования, интервью, пилоты и не читать будущий decision_review.md в этой фазе.

## Отбор

Выбери несколько ближайших неизвестных, ответы на которые действительно меняют решение. Расположи проверки от дешёвых к дорогим с учётом зависимостей. Не расписывай много недель работы по всем gaps только ради полного плана; остальные оставь коротким backlog со ссылкой на исходный пробел. Отдельная тема требует согласования глубины.

Интервью — один из методов, а не обязательный ответ. Внутренний разбор сделок, история обращений, наблюдение, расчёт затрат, проверка предложения, стенд или ограниченный пилот могут быть полезнее. Для внутреннего улучшения не строить полный CustDev новой услуги автоматически.

## Результат: outputs/customer_discovery_plan.md

Коротко укажи цель и решение, затем карточки выбранных ближайших проверок:

- вопрос/причинное звено и ссылка на gap/основание;
- метод, единица/выборка и baseline (или его отсутствие);
- наблюдаемый результат/метрика и что будет подтверждением, опровержением, недостатком данных;
- срок и владелец, если известны; предложения явно пометить;
- ожидаемое доказательство, условия допуска/остановки и следующий выбор при каждом исходе.

Не переписывай список всех известных фактов. Не дублируй одну карточку под разными неизвестными. Если части гипотезы имеют разные зависимости, раздели их: простой внутренний перенос методики не должен ждать проверки всей новой партнёрской модели.

Порог без эмпирического обоснования — предложение для согласования, не доказанный стандарт. Указывать, от какого фактического события отсчитывается срок. Отсутствие причин в учёте не равно отсутствию проблемы; сначала может понадобиться построение baseline. Успешный baseline не доказывает эффект изменения. Проверка измеряет причинный переход целиком, а не удобную промежуточную метрику.

## Если выбраны интервью

Определи релевантную роль и ситуацию/критерий отбора, ограничения выборки. Дай короткий поведенческий гайд только для выбранной проверки: последний реальный случай → нынешнее решение/альтернативы → последствия/затраты → участники решения. Не спрашивать «купили бы вы», не подсказывать желаемый ответ. Не создавать общий большой гайд, если интервью не ближайший шаг. Ролевая симуляция не заменяет интервью.

План не разрешает фактический контакт с людьми, изменения production, доступы или обязательства. Такие действия выполняются только по отдельному разрешению. Записать нужные условия будущей проверки, не выполнять их в аналитическом прогоне.

## Самопроверка

По .clinerules/40-run-quality.md проверить логику положительного/отрицательного/неопределённого исходов каждой выбранной карточки. Например, «ни в одной сделке не найдено пересечение» не означает «ни одна сделка не обходится без пересечения». Не запускать скрипты проверки формулировок. Не создавать детальные карточки для далёких шагов, пока ближайшая проверка может остановить направление.

Сохрани результат и затем отметь завершение в progress.md. Следующий этап — hypothesis-decision-review; наличие подробного плана само по себе не является валидацией гипотезы.
