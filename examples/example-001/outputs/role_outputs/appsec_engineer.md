# Анализ роли: AppSec Engineer

Персона `knowledge-base/personas/application-security-engineer.md` — initial profile, `source_interviews: []`, confidence: low. Используется как слабый supporting context, не как первичное evidence.

## Боль

Приоритет: CRITICAL

AppSec держит очередь SAST между coverage «просканировать всё» и глубиной по системам, которые реально важны. При ограниченной ёмкости FIFO ставит бизнес-критичный репозиторий в один ряд с низкорисковым. Операционный удар: нельзя быстро ответить на смену приоритета бизнеса, решения о порядке приходится объяснять разработчикам без формальных критериев. Бизнес-удар: findings в важных системах приходят позже, чем команда готова их чинить. Срочность высокая, пока wait time очереди сопоставим с релизным циклом.

Персона (слабый сигнал): fragmented tooling, ручные процессы, которые не масштабируются, сложность связать technical findings с business impact.

## Новые проблемы

- Когнитивная нагрузка: каждый bump очереди — отдельное решение без единого источника критичности
- Политическое давление delivery-команд «пропустите наш релиз»
- Нет воспроизводимости: завтра другой инженер поставит другой порядок
- Риск манипуляции метриками: «мы приоритизируем» без следа, кто и почему
- Дополнительная операционка поверх уже существующего triage findings
- Bus-factor: очередь живёт в голове дежурного AppSec

## Альтернативы

- Policy-driven порядок (tier, production exposure, regulated data)
- Metadata-based automation, если criticality живёт в CMDB / service catalog
- Risk-based scanning вместо ручного bump
- Увеличить ёмкость сканера / параллелизм
- Оставить FIFO и эскалировать только инциденты
- Текущий workaround: ручной reorder через чат, когда «кричат громче»

## Контекст отказа

- Длительность скана мала относительно cadence релизов — очередь не является узким местом
- Данных о бизнес-критичности нет или они устарели — ручной контроль даёт случайный порядок
- Низкая зрелость процесса: нет владельца очереди, нет правил исключений
- Политическое давление делает любое ручное решение неустойчивым
- Уже внедрён automated risk-based порядок

## Границы применимости

### Работает когда

- Wait time блокирует появление findings по критичным репозиториям
- Есть хотя бы грубый tier / owner / business unit
- 10–50 проектов, один-два людей, которые реально крутят очередь
- Ручные исключения поверх policy, с коротким сроком жизни

### Не работает когда

- Automated risk-based scanning уже задаёт порядок
- FIFO не создаёт боли (ёмкость достаточна)
- AppSec не имеет доступа к контексту критичности в момент решения

### Вредит когда

- Решения нельзя audit / reproduce
- Разработчики обходят или геймят очередь
- Ручной контроль подменяет, а не дополняет policy
