# Анализ роли: Enterprise Developer

Персона `knowledge-base/personas/enterprise-developer.md` — initial profile, `source_interviews: []`, confidence: low. Используется как слабый supporting context, не как первичное evidence.

## Боль

Приоритет: SECONDARY

Разработчик не покупает приоритизацию очереди и не крутит её. Его боль — предсказуемость: когда закончится SAST, не вылезет ли finding в последний момент, не сдвинут ли чужой «критичный» проект его релиз. Операционный удар: ожидание scan results в CI, повторные прогоны, эскалации в чат. Бизнес-удар: сорванный или нервный релиз, superficial patches «лишь бы pipeline стал зелёным». Персона (слабый сигнал): findings без контекста, false positives, напряжение между дедлайном и remediation.

Гипотеза адресует эту боль только если порядок очереди прозрачен и правила понятны. Непрозрачный ручной bump боль усиливает.

## Новые проблемы

- Perceived unfairness: «их репозиторий всегда едет первым»
- Нет transparency, кто и почему изменил порядок
- Политическое давление на AppSec со стороны delivery
- Поведение «всё критично»: команды учатся эскалировать, а не чинить
- Смещение фокуса с качества кода на манипуляцию очередью
- Ещё один непредсказуемый gate в и без того шумном CI

## Альтернативы

- Shift-left / pre-commit / PR-time scanning для предсказуемого локального цикла
- Фиксированные scan windows / SLO на время очереди
- Self-service «запросить приоритет» с правилами, а не личной договорённостью
- Увеличить throughput сканера
- Игнорировать очередь и чинить findings по факту, если gate не блокирует merge
- Текущий workaround: эскалация в Slack / «позовите AppSec»

## Контекст отказа

- Критерии приоритизации не опубликованы
- Release deadlines игнорируются при bump соседнего проекта
- Есть informal bypasses — формальная очередь теряет смысл
- Blocking SAST на каждом пайплайне при длинной очереди разрушает cadence
- Нет visibility в изменения очереди: разработчик узнаёт о задержке, когда уже поздно

## Границы применимости

### Работает когда

- Правила приоритизации documented и предсказуемы
- Команда видит ETA скана и причину deprioritization
- Ручной bump — исключение с объяснением, не ежедневный режим
- Findings приходят достаточно рано, чтобы remediation не убивала релиз

### Не работает когда

- Изменения очереди opaque
- Throughput сканов уже достаточен для release cadence
- Разработчик не является пользователем очереди и не получает от фичи ничего, кроме сюрпризов

### Вредит когда

- Возникает гонка «кто громче назовёт себя critical»
- Фокус смещается с quality и remediation на queue manipulation
- Чужой bump систематически блокирует merge без escalation SLA
